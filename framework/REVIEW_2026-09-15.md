## 0. 一句话结论

框架工程质量不错（56 tests 全绿、账本/闸门/σ 归因都落地了），bug 产出也真实可观。
但有三个层面的逻辑问题需要在继续"多引擎铺量"之前处理：

1. **研究主张与证据脱节**：论文核心是 "diagnosis-conditioned co-evolution"，
   但目前几乎所有 verified bug 来自零 LLM 的定向脚本（frame_fuzz、dml_hunt、
   xengine、corpus_hunt）+ 人工裁决；Gate 2 配对实验一次没跑；roadmap §6 里也没有它。
2. **bug 计数有可被审稿人一击即溃的软点**：至少 1 个 DataFusion "bug" 实际不是 bug
   （DF-C，我用 PG 16.2 验证了），2–3 个 DuckDB 家族属于"未定义语义/debug 开关"类，
   1 个已被自己降级却仍计入总数（F13）。19 族里保守可辩护的约 12–13 族。
3. **若干代码级逻辑缺陷会系统性地扭曲结果**：跨引擎多数表决无最小法定人数
   （15/108 个 divergence 是 2 引擎"平票"）、plan-variant 的 8 条压缩/位打包轴在
   内存库上是空操作、σ 身份只看 fix_set 导致过合并、bandit 仍按 candidate 而非
   实例化记账（A14 未关闭）、DCE 预算按 probe 数而非 SQL 执行数计。

## 1. 这个项目在做什么（我的理解）

**目标**：在 DBMS 上发现逻辑 bug（错结果/崩溃/INTERNAL），并把"发现"与"诊断/修复"
两侧耦合起来：Fixer 侧的确定性诊断 σ（优化规则二分 + plan diff + 版本梯）定义
Hunter 侧下一步的搜索邻域（DCE），LLM 只出候选和假设，**从不写 verdict**。

**实际管线**（以 `scripts/corpus_hunt.py` / `co_evolution.py::ingest_hit` 为主路径）：

```
seed 语料(1069 条历史回归) ──规则变异/LLM 特征定向──> 查询
   → 确定性闸门 is_usable_for_oracles
   → 健全 oracle：TLP / NoREC / plan-variant(33 规则+执行模式开关) / crash
   → Fixer：ddmin 最小化 + 重放确认
   → σ = (fix_set | plan_diff, ν)  → 族去重
   → DCE：围绕最小复现做算子/子查询形态/NULL/类型/数据扰动 → 再过 oracle
   → 不健全信号(跨版本/跨引擎/LLM 等价)只能产 divergence，需 sound promotion
```

**实际战果的来源分布**（从 FINAL_REPORT 效率表和 ledger 反推）：

| 来源 | 主要家族 | LLM |
|---|---|---|
| corpus_hunt + DCE（零 LLM） | F1、F2、F3、F5、F6 | 0 |
| frame_fuzz 定向枚举（828k 组合） | F10（SIGFPE + 34 repros） | 0 |
| dml_hunt | F11 | 0 |
| xengine 4 引擎差分 | DF-A~F、SQLITE-A、F13、F7 佐证 | 0 |
| llm_feat*/llm_rules*（LLM 特征定向） | F7、F12 及若干 F1/F3 成员 | 22–33 次/轮 |
| main.py 主循环（co-evolution 本体） | 早期 F1（iteration 0） | 417 次/80 轮 |

→ **co-evolution 主循环本身几乎没有独立产出**，产出来自 oracle 栈 + 定向脚本 + DCE。
这不是坏事（DCE 本来就是论文机制），但论文叙事必须跟这个事实对齐（见 §4.1）。

## 2. 逻辑问题清单

### 2.1 研究层面

**P1. Gate 2（配对对照实验）从未执行，但 roadmap 已转向"多引擎铺量"。**
`NEXT_RESEARCH_PLAN` §6–§8 设计得很好（臂 A–J、shuffled-diagnosis 负对照、10 seeds
× 10k 有效执行、bootstrap CI），但 `STATUS_AND_ROADMAP` §6 立即执行清单 6 项里没有一项
是它。当前对 H1–H3 的证据仍是零（README/RESEARCH_PLAN 自己也承认）。
对标 SIGMOD，审稿人第一个问题就是"你的机制比 QPG/random 好多少，CI 是什么"。
→ **[建议]** 把 Gate 2 pilot（臂 B/C/D/F/G 各 ≥5 seeds × 10k）提到清单第 1–2 位，
否则论文只能写成 bug-hunting campaign report。

**P2. "DCE 邻域命中率高"的证据被成员判定方式污染。**
`co_evolution.py::_expand_family` 用"禁用父族 fix_set 也能消掉这个 hit"判定成员
（1 次执行 vs 120 次全二分）。但 §2.3 会说明：禁用 `filter_pushdown`/`deliminator`
能"消掉"大量不相关 bug（回避≠归因，代码注释自己也写了）。于是：
- "deliminator 家族 31 探针 19 命中" 中有多少是真同根因、多少是被 fast-path 吞掉的
  新族，目前不可知；
- 这同时压低了"新族数"（对 DCE 不利）又抬高了"命中率"（对 DCE 有利），方向不定。
→ **[建议]** 成员判定至少要求：父 fix_set 消掉 ∧ 该 hit 自身的 S1 ⊆ 父 fix_set
（两次执行以内可做：先禁父集，再禁父集之外的全部规则看是否仍失败）。

**P3. SQLancer 基线不足以支撑"7.8M checks → 0"的对比。**
- 每引擎 900 s、单 seed、只用默认 oracle（TLP/NoREC），没跑 PQS、CERT、`--qpg`；
  我方是 ~8.5 h 墙钟 + 数十个定向脚本 + 人工账本。这不是同预算对照。
- SQLancer 对 DuckDB 历史上报了数百个 bug；1.5.5 跑 15 分钟为 0 是意料之中，
  审稿人会要求 ≥24 h × 多 oracle × 多 seed。
- **[已验证] STATUS §4.1 "SQLancer 同病（无索引）"是错的**：
  `sqlancer/src/sqlancer/postgres/gen/PostgresIndexGenerator.java` 生成
  btree/hash/gin/gist/brin/spgist、表达式索引、opclass、ASC/DESC/NULLS、partial WHERE；
  另有 Update/Delete/Vacuum/Cluster/Analyze/Set 生成器 → HOT chain、统计操纵这些面
  SQLancer 已经打过数年。PG index-presence oracle 的预期产出应下调（见 §3.2）。
→ **[建议]** (a) SQLancer 至少 4 h × 3 seeds × {TLP, NoREC, PQS, CERT, QPG} 每引擎；
(b) 补一个"grammar gap"实验：把我方每族的最小复现喂给 SQLancer 的 AST，证明其
grammar 生成不出 ASOF/frame-inversion/MERGE NMBS 等形状——这比"它 0 我 19"有说服力。

**P4. 目标版本新鲜度风险。**
- DataFusion 54.0.0（2025-01）—— DataFusion 月更，到 2026-09 至少落后 ~12 个大版本。
  DF-A/B 已知对应 #12955（open），其余 4 族很可能已修。
- PostgreSQL 16.2（2024-02）—— 16.x 已有多个 minor；16.2 上任何发现都要先在 16.latest
  复核。
- DuckDB #23979 的例子已说明问题：fix 已 merge 但未 release，我们仍算 F1 成员。
→ **[建议]** 报告前统一在**各引擎最新 release + main 分支**复核；论文表里加
"still reproduces on main as of <date>" 列。这是 dev-confirmed 的前提。

### 2.2 bug 计数的健全性（逐族审）

| 族 | 问题 | 严重度 | 处置建议 |
|---|---|---|---|
| **DF-C** `list \|\| NULL` | **[已验证] 不是 bug。** PG 16.2：`ARRAY[1,2] \|\| NULL::int[]` → `{1,2}`，`NULL::int[] \|\| ARRAY[3]` → `{3}`。DataFusion 与 PG 一致；DuckDB 才是少数派（自家 `list_concat([1],NULL)` 也返回 `[1]`，只有 `\|\|` 传播 NULL）。该 divergence 记录 `n_engines_ok=2`（PG/SQLite setup_error），所谓"多数表决"是 DuckDB 单参照 | 高 | 从 DF 家族删除；修 §2.3-C1 |
| **F13** `(NULL,NULL) IS NULL` | FAMILY_LEDGER 已写 "Downgraded: spec-reading divergence, not a bug claim"，但 STATUS 表和 FINAL_REPORT headline 仍把它算进 12/19 | 高（自相矛盾） | 移出计数，放"spec 观察"节 |

### 2.3 代码级逻辑缺陷

**C1. [已验证] 跨引擎多数表决没有最小法定人数。**
`scripts/cross_engine.py` L133–146：只要 `len(set(canon.values()))>1` 就记 divergence
并算 `odd`，`n_engines_ok` 可以是 2（两票平局时 `odd` 取决于 Counter 顺序）。
`results/xengine_4way`：108 条 divergence 中 **15 条 n_engines_ok=2**
（odd=sqlite 9、datafusion 5、postgres 1）。DF-C 即出于此。
→ 要求 `n_engines_ok >= 3` 且 plurality 票数 ≥ 2 才产 verdict；2 引擎只能记 `pairwise_divergence`。
另外 DuckDB 方言（`INT[]`、`[1,2]` 字面量、`POSITIONAL JOIN`）导致 PG/SQLite setup_error
的 case 应在生成阶段过滤，否则 4-way 实际退化成 2-way。

**C2. [已验证] plan-variant 的 8 条存储轴在内存库上是空操作。**
`oracles/plan_variant.py` 的 `bitpack_*`、`compress_*` 变体在 setup 之后才 `SET
force_compression`，且 `DuckDBRunner` 用 `:memory:`、从不 CHECKPOINT。实测：
`pragma_storage_info` 在 SET 后仍是 `Uncompressed`，`CHECKPOINT` 后才变 `RLE`。
`scripts/dml_hunt.py` L62–67 已经意识到并加了 `FORCE CHECKPOINT`，但 plan_variant
（主 oracle）没有。→ 这 8 个变体每次多花 8 次执行、零信息；要么加 `FORCE CHECKPOINT`
（并在 setup 前 SET），要么删掉。

**C3. 变体 teardown 用硬编码"默认值"而非 RESET。**
`PRAGMA threads=16`、`perfect_ht_threshold=12`、`late_materialization_max_rows=50`、
`dynamic_or_filter_threshold=50`、`debug_window_mode='window'`……本机 threads 恰好 16，
换机器或换版本默认值就漂了，之后所有 baseline 都在被污染的状态下跑。
→ 全部改 `RESET <setting>`；或每个 variant 用 `clone_fresh()` 的独立连接。
同理 `bisect.py` 的 prelude 在同一连接上累加（`SET disabled_optimizers` 覆盖式尚可，
但 `PRAGMA threads=1` 没有复位）。

**C4. σ 身份 = fix_set 单独决定 → 过合并；flaky 路径 → 过分裂。**
`signature.py::_signature`：`fix_kind in (single, minimal_set)` 时 key 只含 fix_set。
- 任何"关 `filter_pushdown` 就消失"的 bug 都是同一族——F12 被并进 F3 就是这样发生的
  （ledger 自述"σ over-merged... re-keyed manually"）。手工 re-key 意味着 P5"第三方可重算"
  不再成立。
- 反面：F5 flaky 在 `baseline_rounds=3` 下 3/3 都失败的概率不低（默认 37% 失败率下
  ≈5%，但 358 次出现里会多次通过），一旦被当作 stable 就进入全二分，得到随机 fix_set →
  5 个碎片 key。
→ **[建议]** (a) 身份 = `(fix_set, class(plan_diff))`，plan_diff 用算子名的**最小变化子树**
而非全 plan 算子差集；(b) `baseline_rounds` 提到 5–6，并在 S1 确认后再做一次
"threads=1 复判"，任何被 threads=1 消掉的先归 flaky_parallel；(c) 保留手工合并，但把
合并规则写成代码里的 `family_overrides.yml`，让 FINAL_REPORT 可重算。

**C5. bandit 仍按 candidate 记账（NEXT_RESEARCH_PLAN A14/A15 标"关闭"，实际未关）。**
`agents/bug_hunter.py::learn_from_feedback` 只由 `co_evolution.py` 在有 candidate 时调用；
一个类别生成 8 条查询零命中时 `tries` 不变。UCB 的探索项因此失真，
且 `random_category` 模式仍收 guideline/rewrite_memory 反馈（A4）。
→ 在 hunter 每次实例化查询后立即 `bandit.update(arm, wasted=False, novel_cells=...)`，
candidate verdict 只追加 `true_bug` 奖励。

**C6. DCE / 效率报表的"执行数"口径不一。**
`dce.py::expand` 把每个 probe 记 1 次 `probes_executed`，但 `_check_probe` 对每个 probe
跑 TLP(4) + NoREC(2) + plan-variant(1+33×3) ≈ **100+ 次 SQL 执行**。`dce_budget=2000`
实际允许 ~20 万次执行；FINAL_REPORT 的 "52k execs" 和 "yield fam/1k exec" 因此
不可比（不同脚本口径不同）。→ 统一用 runner 层的执行计数器（`eff.count`）作为唯一口径。

**C7. 版本梯 ν 把"旧版报错"一律判 `recent`。**
`signature.py::_version_ladder`：旧版 `error is not None` → `"recent"`。旧版不支持的语法
（ASOF、MERGE、QUALIFY…）会被误判为回归。→ 区分 parser/binder 错误（`unknown`）与执行成功但结果不同（`recent`）。

**C8. 文档/配置漂移。**
`config.yml: version "1.5.2"` vs 全部主张基于 1.5.5；README "36 tests" vs 实际 56；
`main.py --engine` 只有 duckdb/postgres，sqlite/datafusion 只在脚本里。
→ 加 run manifest（已计划 Phase 0）真正落地，并让 `final_report.py` 校验版本一致。

**C9. 小项。**
- `tlp.py::_SKIP_PATTERN` 用 `\bover\b`、`\brank\s*\(` 等词法匹配，列名/别名撞词会误跳；
  可接受但应统计 skip 率。
- `plan_variant.py` 中 `no_optimizer` 变体 teardown 用 `PRAGMA enable_optimizer`，
  但若 bisect 之前留下 `disabled_optimizers` 非空，`enable_optimizer` 不会清它。
- `_ddmin` 的 `complement` 分支在 `n` 增长时可能重复测试同一子集，浪费预算（可加 memo）。

### 3.2 PostgreSQL：修正诊断、下调目标

- 诊断"所有 seed 无索引、SQLancer 同病"不成立（§P3）。PG 是被 SQLancer/SQLsmith/
  自家 regress 打得最透的引擎，plan-variant 26 轴 × 数千查询 0 命中本身就是信号。
- **[建议]** 把目标从 10–30 改为 **0–3，并把"成熟引擎上的诚实阴性"写成结果**：
  与 SQLancer 同为 0 是可发表的对照点。
- 若仍要打，选**真正 fuzz 历史短的面**（而不是索引 AM）：
  - PG16 新增：`SQL/JSON` 构造函数 `JSON_ARRAY/JSON_OBJECT/JSON_ARRAYAGG`、
    `IS JSON` 谓词、`pg_stat_io`；PG15 新增 `MERGE`（+RETURNING 是 17）、
    `UNIQUE NULLS NOT DISTINCT`、`range_agg/multirange` 运算；
  - 分区表 + `enable_partitionwise_*` + 运行时剪枝 + `MERGE`/`ON CONFLICT` 跨分区；
  - 窗口 `EXCLUDE CURRENT ROW/GROUP/TIES` + `GROUPS` 模式（对应 F10 的 PG 版）；
  - `incremental_sort` + `memoize` 与相关子查询的组合（都是 13/14 才进的代码）。
  这些能直接复用现有 plan-variant/TLP 栈，不必新建 index-presence oracle。
- 若做 index-presence oracle，至少要与 SQLancer 区分：**同一连接内 UPDATE 后立即
  index-only scan** 的顺序敏感测试（HOT 链需要写-读交错），这是 SQLancer 的
  无状态 oracle 不做的。

### 3.3 第 5 引擎：TiDB+MySQL 成本高、假设强

- 环境事实（BRIEF）：无 sudo/docker。`tiup playground` 需要下载 TiDB/TiKV/PD 三个二进制
  并起集群，MySQL 还得另装——两套系统、内存开销大。
- "TiDB 自承诺 MySQL 兼容 → 差分即 bug"过强：TiDB 有一整页文档化的不兼容列表
  （自增 ID 分配、默认排序、`GROUP_CONCAT` 长度、某些函数精度……）。差分仍需人工裁决，
  优势不如宣称的大。
- **[建议]** 先用 **chdb**（`pip install chdb`，ClickHouse 进程内版）——零安装、
  与现有 `targets/` 模式一致（DuckDB/DataFusion 都是 in-process），ClickHouse 的
  SQL 语义分歧多、fuzz 历史相对短（它自己主要用 AST fuzzer 而非逻辑 oracle）。
  TiDB 留作 future work。

### 3.4 框架层

- **oracle 表新增"触发条件"维**：default-path / user-setting / debug-setting /
  unspecified-semantics，每族标注。这比"4 类 oracle"更能回应审稿人的"这算 bug 吗"。
- **index-presence 与 stats-manipulation** 本质都是 plan-variant 的干预基扩展
  （多一类 prelude），不必另起 oracle 类；写进 `bisect.py` 的干预基更能同时服务 σ 归因。
- **DataFusion "0 hit on 26 toggles"** 的结论要谨慎：DF 的 toggle 大多是 optimizer rule，
  而 DF 的 bug 在 executor/analyzer 层。可试的 DF 干预基：`datafusion.execution.target_partitions`
  (1 vs N)、`batch_size` (1/2/8192)、`coalesce_batches`、`prefer_hash_join`、
  `repartition_*`、`enable_round_robin_repartition`——这些才是 DF 的"执行模式开关"。

### 3.5 论文叙事：先决定讲哪个故事

当前数据支持两种写法，二选一，不要混：

**故事 A（机制论文，原计划）**：DCE 比 QPG/random 更快找到新族。需要 Gate 2 数据；
bug 数只是次级指标；DuckDB 一个引擎足够，PG/SQLite/DF 作外部有效性附表。

**故事 B（发现论文）**：健全 oracle 栈 + 确定性诊断去重 + 定向枚举，在 4 个引擎上
找到 N 个 dev-confirmed bug，SQLancer 同预算为 0。需要：公平的 SQLancer 基线、
dev 确认、严格的保守计数、"grammar gap"分析。co-evolution 只是其中一个组件。

从 §1 的产出来源看，**现状更接近 B**。如果要坚持 A，Gate 2 必须是下一步；
如果转 B，就把 roadmap 里"co-evolution framework evaluation"的措辞收回来，
避免审稿人拿 A 的标准审 B 的证据。

## 4. 值得肯定、应保留的部分

- verdict 与 LLM 的隔离、账本、`no_llm` 硬门、`skipped_nondeterministic` 不计数、
  README 的 honesty boundaries——这些是同类 LLM-fuzzing 工作里少见的纪律。
- σ 归因 + `pervasive` 降级 + flaky 闸门的思路正确，只是实现粒度需要调（§C4）。
- F10 是真金：SIGFPE 进程级崩溃 + 负 count + 静默垃圾值，PG 同查询给 0（我复核了），
  且绕过了 #23589/#24831 已落地的 parser 检查——这一族就够一个 headline。
- F7 interval CSE 非同余、F2 重复分区键、F11 NMBS swapped-sides 残余面——
  都是机制清楚、可直接写 issue 的发现。
- xengine 4-way 作为**佐证**（F2/F7 被 PG 独立确认）用得很好；问题只在把它当**发现**
  oracle 时的法定人数。
